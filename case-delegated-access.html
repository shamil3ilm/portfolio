Case study · Payments API

Letting providers act for their customers, without handing over the keys

Payroll and bookkeeping companies run payments for many small businesses. They need to work inside each customer's account, but the customer has to stay in control, and every action has to be traceable.

Software Engineer, Zil Money2026PHP · Laravel · MySQL

The problem

A service provider, such as a payroll company, manages payments for many businesses. Asking each customer to share their login is unsafe. Giving the provider broad access is worse: one mistake, or one bad actor, could move money in any of those accounts.

The platform needed a way for a provider to act as a customer, with limits the customer can trust and a record of everything the provider does.

What I built

  1. The customer creates a one-time connect key. It is valid for a year and works once. Asking again returns the same unused key, so spare keys never pile up.
  2. The provider redeems the key to connect. A used, expired or unknown key is refused, and so is a customer who is already connected to another provider, or a provider trying to connect to itself.
  3. The provider then uses the same API the customer's own software uses, on the customer's behalf. Instead of building a second, separate API, I added an "acting for this customer" layer to the existing endpoints across the payment services, so providers get the same features and the same checks.
  4. Every call is checked and recorded. Allowed calls are logged. Refused calls all get the same short reply, "Access denied", whatever the reason, while the real reason is written to the log.
  5. Payment updates are copied to the provider only if it subscribes. Updates such as "payment created" can be mirrored to the provider as well as the customer.

The guardrails that mattered

  • The customer's approvals stay the customer's. A provider can create a payment, but it can't approve one that is waiting for the customer's own approvers.
  • No record, no action. If a call can't be attributed and logged, it is refused rather than allowed through unrecorded.
  • One answer for every refusal. Several different reasons sit behind the same reply, so nobody can probe which customers exist or why they were turned away. The log keeps the detail.
  • Suspension works both ways. Suspending a customer's connection, or the provider itself, stops its requests straight away.

Why reuse the existing API? A separate provider API would drift from the main one: new features would arrive late, and every rule would exist twice. Layering access on top keeps one set of rules for everyone.

What I'd point out

Most of the work wasn't the happy path; it was deciding what happens when something is off: an old key, a suspended account, a payment that belongs to someone else's approval process. Each of those has one clear outcome, and each is recorded.
