Seeing what every AI call costs, and when it fails

A payments platform used AI in many places, from reading receipts and payroll PDFs to drafting analyses. The spend arrived as one provider bill, and a failed call was easy to miss.

Software Engineer, Zil Money2026PHP · Laravel · MySQL

The problem

  • One bill, no breakdown. There was no way to tell which feature or which model the cost came from.
  • Failures were quiet. A call that failed showed up, at best, somewhere in the logs, so nobody could say how often each feature was failing.
  • Speed was a guess. Slow calls were noticed by users before they were noticed by the team.

What I built

  1. One record for every AI request. Each record holds the feature, model and provider, the tokens in and out, the cost, how long it took, whether it succeeded, and the error if it did not.
  2. Failures are recorded by design. The record is written in a step that runs whether the call succeeds or fails, so a failure can never skip the log. Records are only ever added, never edited.
  3. Tracking lives in the shared AI client, not in each feature, so every feature that calls an AI model is tracked without extra code.
  4. Each group of features runs under its own provider account, so spend is separated at the source as well as in the log.
  5. A dashboard on top: filter by date, status, feature, model and provider account; totals for calls, tokens, cost and average response time; breakdowns by feature and by model; and a 24-hour health view per provider account with its call count, error rate and last successful call.

The lesson

Because the tracking sits in the one client every feature already uses, a new AI feature is tracked from its first call. Nobody has to remember to add it.
